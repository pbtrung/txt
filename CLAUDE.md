# CLAUDE.md

Guidance for Claude Code (or any agent) working in this repository.

## What this is

A personal document-storage system. The design (`docs/data_model.md`) stores everything in one InstantDB app plus Cloudflare R2: InstantDB holds only `$users` (Firebase-verified identity + a wrapped key hierarchy), `credStore` (encrypted key-material blobs — `r2_config`/`path_key`/`db_key`/`display_name`, one row per owner/subject pair), and a page-store (`dbMeta`/`pages`/`activeReaders`) for **one SQLCipher-encrypted SQLite database per user**, paged remotely into R2 a page at a time. The actual application schema (documents/parts/bookmarks — see `txt/sqlcipherBuilder.ts`'s `SCHEMA_SQL`) lives entirely _inside_ that per-user SQLCipher file; InstantDB never sees plaintext rows for it, only an opaque, client-encrypted R2 object key directly on each `pages` row (`path` — no separate pointer-file entity).

This repo has three parts: the **TypeScript CLI** (`txt.ts`) for administering an account, the **React viewer** (`ui/`) end users actually unlock/read/write through, and a **Cloudflare Worker** (`worker/`, deployed alongside `ui/`'s static build as one Worker-with-static-assets resource) that's the one server component the whole design needs — it verifies a Firebase ID token and mints a short-lived, prefix-scoped R2 credential for it, so no browser session, admin included, ever holds a static R2 key. `--migrate` imports documents from an external SQLite snapshot with its own schema (see `txt/owner.ts`) into an already-`--init-admin`-provisioned InstantDB account, through the same page-by-page R2 transport `--init-admin` itself uses.

Read `docs/data_model.md` (entities, permission rules), `docs/key_hierarchy.md` (how the encryption keys nest), `docs/protocols.md` (ingest/read/share/GC flows), `docs/r2_credentials.md` (R2 credential broker, account provisioning), `docs/auth.md` (sign-in flow), and `docs/crypto.md` (the AEAD/KDF/KEM blob format) before making any design-level change — they're the source of truth, not this file.

## Commands

CLI:

```
node txt.ts --init-admin <creds.json> [-v|--verbose]
node txt.ts --clean-bucket <in.db> --creds <creds.json> [-v|--verbose] [--dry-run] [-y|--yes]
node txt.ts --migrate --from <in.db> --from-creds <from_creds.json> --to-creds <to_creds.json> [-v|--verbose] [--dry-run] [-y|--yes]
```

Entry point is `txt.ts` → `txt/cli.ts`'s `run()` → one of `AdminInitializer` (`adminInit.ts`), `TxtBucketCleaner` (`bucket.ts`), `Migrator` (`migrate.ts`).

`ui/` + `worker/` (deployed together as one Cloudflare Worker with a static-assets binding — see README.md for the full setup/deploy walkthrough, including the three dashboard Variables/Secrets `worker/r2Creds.ts` needs):

```
npm run ui:dev           # Vite dev server
npm run ui:build         # tsc -b ui/tsconfig.json + vite build -> dist/, then build-integrity.mjs
npm run ui:test          # vitest
npm run worker:dev       # wrangler dev, serves dist/ + worker/index.ts locally
npm run worker:typecheck # wrangler types (regenerates worker/worker-configuration.d.ts) + tsc -b worker/tsconfig.json
WORKER_NAME=<name> npm run deploy -- <build-creds.json>  # ui:build then wrangler deploy --name
```

## Architecture map

- `instant.schema.ts` / `instant.perms.ts` — InstantDB schema/perms, pushed with `npx instant-cli@latest push [schema|perms] --app <id>`. Changes here need a real push to take effect against the live app; `push schema` reports "No schema changes to apply!" for changes it doesn't diff (confirmed: `onDelete` link config is one such case) — don't trust that message alone when a link's cascade behavior changed.
- `txt/crypto.ts` — `CryptoEngine`: the blob format (`docs/crypto.md`) via the vendored leancrypto WASM module (Ascon-Keccak AEAD + HKDF-SHA3-512), plus HMAC-SHA3-256 username hashing via native Node crypto.
- `txt/sqlcipherBuilder.ts` — raw SQLite C API wrapper (`open`/`insert`/`close`, plus the one-shot `run` for initial schema creation) against whichever VFS the caller registers.
- `txt/r2Vfs.ts` — `R2Vfs`: adapts the vendored in-memory `sqlcipher/js-vfs.mjs` into a page-by-page-over-R2 VFS by prefetching all current pages up front, letting `xRead`/`xWrite` run synchronously against that in-memory buffer, then diffing against the original snapshot to find dirty pages for an explicit async flush.
- `txt/remotePageStore.ts` — `RemotePageStore`: the read (`fetchPage`) and write (`commitPages`) primitives that talk to InstantDB (admin SDK) + R2 for the page store.
- `txt/pagePointer.ts` — `pages.path` encoding: only `raw_key` (`generateRawKey`'s output) is ever encrypted (`encodePagePointerContent`, wrapped under `path_key`), base64-encoded directly into `pages.path` — no separate pointer-file entity or upload step. The real R2 object address is `${r2Prefix}/${raw_key}`, where `r2Prefix` is a pure function of `auth.id` (never encrypted, cheap to recompute, left out of the encrypted blob entirely).
- `txt/owner.ts` — `TxtOwner`: reads the source SQLite schema `--clean-bucket` and the "from" side of `--migrate` operate against — user/key resolution, known R2 paths, part/metadata decoding.
- `txt/instantSignIn.ts` / `txt/firebaseAuth.ts` — Firebase password sign-in → InstantDB `auth.id` exchange (`signInToInstant`, shared by `--init-admin` and `--migrate`).
- `txt/creds.ts` / `txt/initAdminCreds.ts` — creds.json loaders. `Creds` (creds.ts) is the source-account shape (`--clean-bucket`, `--migrate --from-creds`); `InitAdminCreds` (initAdminCreds.ts) is the InstantDB-account shape (`--init-admin`, `--migrate --to-creds`).
- `sqlcipher/` — vendored WASM SQLCipher build + its own JS VFS shim. Not hand-authored here; treat as a build artifact (gitignored from prettier via `.prettierignore`, but tracked in git since there's no build step in this repo to regenerate it).
- `ui/src/data/session.ts` — the post-sign-in unwrap chain: queries `$users` (with its linked `dbMeta`) and `credStore` (client SDK, permission-rule-gated), unwraps `user_root_key → umk → credStore.content` to recover `path_key`/`db_key`/`r2_config`. `credStore`'s "own row" is the one where both `owner`/`user` links point back to the caller's own `auth.id` (mirrors `txt/collectGarbage.ts`'s `resolveOwnCredStore`).
- `ui/src/data/instantPageStore.ts` — browser port of `txt/remotePageStore.ts`'s `fetchPage`/`commitPages`, talking to InstantDB via the real client SDK (not the admin SDK — a browser can never safely hold an admin token) and R2 via `aws4fetch`. Unlike the CLI, `commitPages` has to survive a concurrent writer for real: a rejected `dbMeta` CAS update triggers a re-read of `currentVersion` and a retry, up to `CAS_MAX_RETRIES`. `fetchPagesBatch` resolves many page numbers via a bounded number of InstantDB queries (`pageNo: {$in: pageNos}`, paginated via `instaqlPagination.ts`) instead of one query per page number — `dbWorker.ts`'s own open()-time prefetch is its only caller (a known, up-front page list); the lazy on-demand path (`remotePageWorker.ts`'s use of `fetchPage`) can't batch this way, since it doesn't know its next page number until SQLite's own `xRead` asks for it.
- `txt/instaqlPagination.ts` / `ui/src/data/instaqlPagination.ts` — generic, backend/shape-agnostic cursor-pagination loop (`collectAllPages`) for any query that could return thousands of rows for one account: the caller builds its own query for a given cursor and extracts `{rows, hasNextPage, endCursor}`, this just follows the cursor until exhausted. Not shared between the CLI and `ui/` (separate runtimes/tsconfigs, same as `pagePointer.ts`/`base32.ts` already aren't) — two identical copies. `migrate.ts`'s stale-page sweep and `instantPageStore.ts`'s `fetchPagesBatch` are the two current callers. `@instantdb/react`'s `queryOnce()` resolves `{data: {...}, pageInfo: {...}}` as _siblings_ (confirmed against `@instantdb/core`'s own type declarations) — `pageInfo` is never nested inside `data`, easy to get wrong by assumption.
- `ui/src/data/remoteVfs.ts` / `dbWorker.ts` / `remotePageWorker.ts` / `remotePageClient.ts` — the Worker + `Atomics.wait` bridge letting SQLite's synchronous WASM `xRead`/`xWrite` callbacks make a genuinely async page fetch, since `Atomics.wait()` is forbidden on the main/document thread (confirmed against real Chromium). `dbWorker.ts` holds the actual `SqliteDb`/VFS and spawns `remotePageWorker.ts` as a _nested_ Worker purely for page fetches; the main thread only ever talks to `dbWorker.ts` through `dbWorkerClient.ts`'s small RPC protocol.
- `ui/src/data/tempR2Creds.ts` — the only place this app ever builds an `AwsClient`: POSTs `{idToken, prefix, bucket, endpoint}` to `worker/r2Creds.ts`'s `/api/r2-creds` and builds a client from the short-lived credential it returns. `dbWorker.ts` and `remotePageWorker.ts` each mint and periodically refresh their own (two separate Worker contexts, can't share a live client object across `postMessage`), scheduled off the credential's own real `expiresAtMs`.
- `ui/src/data/owner.ts` / `parts.ts` — read `txt_parts.content` directly (brotli-decompress only) — no per-part R2 addressing or AEAD unwrap, unlike the old rqlite-backed design this was ported from; content is already protected by SQLCipher's own page-level encryption.
- `ui/src/state/VaultContext.tsx` — top-level unlock/session state. `unlock(file)` reads a creds.json-shaped file upload, signs into Firebase, exchanges for an InstantDB session (`session.ts`), opens `dbWorker`.
- `ui/scripts/build-integrity.mjs` — runs after `vite build`: adds SRI to `dist/index.html`'s entry tags, writes `dist/manifest.json`/`.sig` (SLH-DSA-signed) and the real `dist/_headers` (CSP/COOP/COEP — the one Cloudflare actually serves, narrower than `index.html`'s own `<meta>` CSP), and bundles `creds/local_index.html` (a self-contained pre-verification page, never uploaded to the CDN).
- `worker/index.ts` — this deployment's only Worker script: dispatches `POST /api/r2-creds` itself, falls through to `env.ASSETS.fetch()` (the `dist/` static build) for everything else. Deployed as a real Worker-with-static-assets resource, not classic Cloudflare Pages Functions.
- `worker/r2Creds.ts` — verifies a Firebase ID token (RS256 via `jose` against Firebase's own public JWKS, issuer/audience pinned to `env.FIREBASE_PROJECT_ID` — never accepted from the request itself) and, if valid, mints a temporary R2 credential for the request's own prefix via R2's local JWT-signing scheme (HS256, no outbound Cloudflare API call). Does not cross-check the prefix against the token's own subject — trusted as given once the token is proven real, a deliberate simplification for a small, admin-curated user base.
- `wrangler.jsonc` — Worker config (`main`: `worker/index.ts`, `assets.directory`: `./dist`). Its own `"name"` is an unused placeholder; the real deploy target always comes from `scripts/deploy.sh`'s required `WORKER_NAME` env var, never this file.

## Non-obvious constraints (confirmed empirically — don't re-derive, don't assume otherwise)

- **InstaQL always returns a linked sub-entity as an array**, regardless of that link's own declared cardinality (`has: "one"` included). `$users.dbMeta[0].id`, not `$users.dbMeta.id` (`ui/src/data/session.ts`'s `firstLinked` guards every linked row for exactly this reason) — treating it as a plain object produces silently `undefined` fields rather than an error, which can propagate a long way before surfacing (e.g. a 0-byte "reopened" database that looks brand new to SQLite, no error until the first real query against it). See the `instantdb-instaql-array-links` memory.
- **The vendored WASM build is compiled with `WASM_BIGINT`**: 64-bit SQLite C API calls (`sqlite3_bind_int64`, `sqlite3_last_insert_rowid`, `sqlite3_column_int64`) take/return real JS `BigInt`, not `Number`. Confirmed empirically, not documented anywhere in the build.
- **`PRAGMA cipher_default_page_size` must be set before `sqlite3_key()` on every open** (create or reopen), matching `SQLCIPHER_PAGE_SIZE` (`constants.ts`). This codec has no plaintext header for SQLite to sniff the real page size from otherwise — omitting this breaks reopening any non-default-page-size database ("unrecognized magic/version bytes for pgno=1").
- **No Asyncify in this WASM build** — genuine on-demand async fetches from inside a synchronous `xRead`/`xWrite` C callback aren't possible. Hence the prefetch-everything-then-diff model in `r2Vfs.ts`, not lazy per-page fetching.
- **`@instantdb/core`'s `Reactor` is browser-only** — its constructor checks `typeof window !== 'undefined' || typeof chrome !== 'undefined'` and silently skips storage/state setup (`this.kv`, etc.) when neither is true, later crashing deep inside `signInWithIdToken()` ("Cannot read properties of undefined (reading 'updateInPlace')") the first time anything actually touches that skipped state. `instantSignIn.ts` calls InstantDB's `POST /runtime/oauth/id_token` endpoint directly instead of using the SDK, for exactly this reason — don't reach for `@instantdb/core` in the CLI; use `@instantdb/admin` (genuinely Node-safe, bypasses permission rules) or plain `fetch` for anything auth-related. The same gate also fires inside a real browser's dedicated Worker (global scope is `self`, no `window`) — `ui/src/data/instantClient.ts`'s `createInstantClient()` works around it with a minimal `globalThis.window = globalThis.self` shim, confirmed safe by reading through every other `window`/`document` reference in `@instantdb/core`'s own source (all independently guarded, OAuth-redirect-specific code this app never exercises).
- **Node's TypeScript strip-only mode doesn't support constructor parameter properties** (`constructor(private x: T)`) — a real syntax transform is needed, not just type erasure. Declare fields and assign in the constructor body instead.
- **R2/InstantDB page round-trips are batched**, not serial or fully unbounded: `RemotePageStore.uploadPages` and `R2Vfs.prefetchPages` both prepare everything up front (pure, no I/O) then issue round-trips `R2_BATCH_CONCURRENCY` (constants.ts) at a time via `Promise.all`.
- **This project's live Cloudflare resource is the newer unified "Workers with static assets" product, not classic Cloudflare Pages** — confirmed via its own dashboard error ("Variables cannot be added to a Worker that only has static assets") when no real Worker script was attached yet. This means `worker/`'s deploy shape is a single Worker entry script (`main` in `wrangler.jsonc`, dispatching routes itself and falling through to `env.ASSETS.fetch()`), not a Pages Functions `functions/` directory — don't reach for that convention here.
- **R2's Temporary Credentials "local signing" derivation** (`worker/r2Creds.ts`, no outbound call to Cloudflare's API) — the runnable reference is [developers.cloudflare.com/r2/examples/authenticate-r2-temp-credentials](https://developers.cloudflare.com/r2/examples/authenticate-r2-temp-credentials/); the prose-only `.../api/s3/temporary-credentials/` page is incomplete/misleading on its own (confirmed the hard way: an earlier implementation built from that page alone used the wrong claim name, was missing required claims entirely, and used the wrong base64 variant — all three produced the exact same unhelpful `<Error><Code>InvalidArgument</Code><Message>X-Amz-Security-Token</Message></Error>` from R2, regardless of which one was still wrong). Use `jose`'s `SignJWT` with claims `{bucket, scope, paths: {prefixPaths}}` (the field is `scope`, not `permission` — `permission` is the separate Temporary Credentials _API_'s own parameter name) plus registered claims `sub` (R2 account ID), `iss` (parent access key ID — this, not the request's own `accessKeyId`, is what R2 uses to look up which parent secret to re-verify the signature against), `aud` (the R2 endpoint's host), `iat`/`exp` via `setIssuedAt()`/`setExpirationTime()` (there is no `ttlSeconds` claim), signed HS256 with the parent secret access key. Then: `accessKeyId` = the parent access key ID reused as-is, `secretAccessKey` = the SHA-256 hex digest of the full signed JWT string, `sessionToken` = plain `base64("jwt/" + <signed JWT>)` (not base64url, despite that being a reasonable-looking guess).

## Verification

**`txt/` (the CLI)** has no test framework configured (`npm run typecheck` only). Verification there has meant hand-written one-off scripts against real building blocks: a real `CryptoEngine`, a real `SqlCipherBuilder`+`R2Vfs` over a real in-memory VFS, a minimal hand-rolled HTTP mock S3 server (list/put/get/delete, path-style, no SigV4 checking), and a stateful fake InstantDB admin object (`transact`/`query` against an in-memory store, following the real `@instantdb/admin` tx builder's `{__etype, __ops}` shape) for anything that doesn't need to hit a real InstantDB app. `global.fetch` gets monkey-patched to redirect specific hostnames to a local mock server when testing Firebase/InstantDB sign-in. These scripts live outside the repo (session scratchpad, not committed) — write new ones the same way rather than assuming a runner exists.

**`ui/`** has a real vitest suite (`npm run ui:test`) following the same real-building-blocks philosophy: a real `SqliteDb`/WASM VFS, a real in-memory R2 "bucket" fronted by a fake `aws4fetch` client, and a stateful fake InstantDB client (`queryOnce`/`transact`) reducing the real `@instantdb/react` tx builder's `{__etype, __ops}` shape — same pattern as the CLI's own admin-SDK fakes, just for the client SDK. `pages.path` is a plain field on the fake `pages` rows themselves, so no second mock server or download step is needed to resolve one. `npm run ui:typecheck` (`tsc -b`) is separate and should also stay clean.

**`worker/`** has no test suite (no framework wired up for the Workers runtime yet) — `npm run worker:typecheck` and a real `wrangler dev` run (hitting `/api/r2-creds` with curl, checking the static-asset fallthrough) are what verification has meant there so far.

`npm run format` / `npm run format:check` (prettier, repo-wide) exist; run format after any edit.

Some things can't be mocked at the HTTP-protocol level without real credentials and need a real run against live infra, with any errors diagnosed from the actual stack trace: the real `@instantdb/admin`/`@instantdb/react` `init()` → live query/transact/storage calls, and `worker/r2Creds.ts`'s actual Firebase JWKS verification + R2 credential mint (a bogus/malformed token is easy to test locally; a real, valid one needs a real Firebase project).

## Commit conventions

Detailed commit messages (imperative subject, bullet-point body explaining what and why), **no AI/Claude attribution ever** (no `🤖 Generated with Claude Code`, no `Co-Authored-By: Claude`), always push after committing. A `/commit` skill (`.claude/commands/commit.md`) automates this.

## Secrets

`.gitignore` blocks all `*.json` except a short explicit allowlist (`package.json`, `package-lock.json`, `tsconfig.json`, `ui/tsconfig*.json`, `ui/src/**/*.json`) — this project repeatedly generates local creds-shaped JSON files with real secrets (Firebase passwords, InstantDB admin tokens, R2 keys, `ui/build-creds.json`'s own SLH-DSA private key). Never commit a JSON file containing real credentials; double-check contents before `git add` on anything JSON-shaped. `wrangler.jsonc` is a `.jsonc` file (unaffected by that `*.json` rule either way) and carries no secrets itself — `worker/r2Creds.ts`'s two real secrets are Cloudflare dashboard Secrets, never written to any file in this repo.
