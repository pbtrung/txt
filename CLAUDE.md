# CLAUDE.md

Guidance for Claude Code (or any agent) working in this repository.

## What this is

A personal document-storage system. Its design (`docs/data_model.md` and its sibling `docs/*.md` files) stores everything in one InstantDB app plus Cloudflare R2: InstantDB holds `$users` (Firebase-verified identity + a wrapped key hierarchy), `keyStore` (a per-account Kyber/X448 keypair, currently unused — kept provisioned against a future feature that needs an asymmetric wrap), `credStore` (encrypted R2-connection-info blobs), and each document as its own `txt`/`txtMetadata`/`txtParts` rows — only the admin account ever owns one. Every other account only ever reads a document through its own `sharedTxt`/`sharedTxtMetadata`/`sharedTxtParts` rows instead — an independent, admin-made copy under a fresh key and R2 prefix that the admin creates for them, never a grant onto the admin's own rows. A document's (or share's) actual text lives as per-part R2 objects, addressed by a random, per-row R2 prefix that's itself only recoverable by decrypting it — InstantDB never sees plaintext content, real object addresses, or unwrapped keys. All three parts below (`txt.ts`, `ui/`, `worker/`) now implement this same design — there is no older design left running anywhere in this repo.

This repo has three parts: the **TypeScript CLI** (`txt.ts`) for administering an account and importing documents, the **React viewer** (`ui/`) end users actually unlock/read/write through, and a **Cloudflare Worker** (`worker/`, deployed alongside `ui/`'s static build as one Worker-with-static-assets resource) that's the one server component the whole design needs — it verifies a Firebase ID token and mints a short-lived, read-only R2 credential for it, so no frontend R2 client uses a static R2 key or has write access. The admin self-row still contains the operator keys in its combined encrypted payload; admin unlock transiently decrypts that payload but discards the key fields instead of retaining or using them. `--ingest` cleans, splits, and uploads every `.txt` file in a directory into an already-`--init-admin`-provisioned InstantDB account as its own `txt`/`txtMetadata`/`txtParts` rows plus per-part R2 objects.

Read `docs/data_model.md` (entities, permission rules), `docs/key_hierarchy.md` (how the encryption keys nest), `docs/protocols.md` (ingest/read/share/GC flows), `docs/r2_credentials.md` (R2 credential broker, account provisioning), `docs/auth.md` (sign-in flow), and `docs/crypto.md` (the AEAD/KDF/KEM blob format) before making any design-level change — they're the source of truth, not this file.

## Commands

CLI:

```
node txt.ts --init-admin <creds.json> [-v|--verbose]
node txt.ts --clean-bucket --creds <creds.json> [-v|--verbose] [--dry-run] [-y|--yes]
node txt.ts --ingest <dir> --creds <creds.json> [-v|--verbose] [--dry-run]
```

Entry point is `txt.ts` → `txt/cli.ts`'s `run()` → one of `AdminInitializer` (`adminInit.ts`), `TxtBucketCleaner` (`bucket.ts`), `TxtIngester` (`ingest.ts`).

`ui/` + `worker/` (deployed together as one Cloudflare Worker with a static-assets binding — see README.md for the full setup/deploy walkthrough, including the three dashboard Variables/Secrets `worker/r2Creds.ts` needs):

```
npm run ui:dev           # Vite dev server
npm run ui:build         # tsc -b ui/tsconfig.json + vite build -> dist/, then build-integrity.mjs
npm run ui:test          # vitest
npm run worker:dev       # wrangler dev, serves dist/ + worker/index.ts locally
npm run worker:typecheck # wrangler types (regenerates worker/worker-configuration.d.ts) + tsc -b worker/tsconfig.json
npm run worker:test      # vitest run worker
WORKER_NAME=<name> npm run deploy -- <build-creds.json>  # ui:build then wrangler deploy --name
```

## Architecture map

- `instant.schema.ts` / `instant.perms.ts` — InstantDB schema/perms, pushed with `npx instant-cli@latest push [schema|perms] --app <id>`. Changes here need a real push to take effect against the live app; `push schema` reports "No schema changes to apply!" for changes it doesn't diff (confirmed: `onDelete` link config is one such case) — don't trust that message alone when a link's cascade behavior changed.
- `txt/crypto.ts` — `CryptoEngine`: the blob format (`docs/crypto.md`) via the vendored leancrypto WASM module (Ascon-Keccak AEAD + HKDF-SHA3-512, plus the `lc_kyber_1024_x448` composite KEM — `kemKeypair`/`kemEncapsulate`/`kemDecapsulate` — used by `adminInit.ts` to provision every account's `keyStore` keypair; currently unused by sharing itself, which wraps a share's key symmetrically instead — see `docs/data_model.md`'s `keyStore` entity).
- `txt/randomToken.ts` — generates and wraps the random, opaque R2-addressing tokens this design uses (`txt.prefix`, `txtParts.path`) — shared by `txt/ingest.ts` (mints fresh ones) and `--clean-bucket`/`--update-db-prefixHash` (which only ever unwrap existing ones).
- `txt/ingest.ts` — `TxtIngester`: `--ingest`'s orchestrator. Resumable by filename only (skips a file already recorded in an owned document's `txtMetadata.catalog.name`); uploads every part of a file to R2 before ever calling `db.transact()`, so a failed file leaves nothing in InstantDB and only orphaned R2 objects for `--clean-bucket` to sweep. Assigns each new document the next `seq` after this admin's current highest.
- `txt/textproc.ts` — `preprocessText`/`splitParts`: cleans raw text (strips control/zero-width/BOM chars, collapses whitespace and blank-line runs) and splits it into `PART_TARGET`-sized, paragraph-bounded chunks. Port of the pre-InstantDB Python design's `txt/textproc.py`, verified byte-for-byte against real runs of it rather than just its source.
- `txt/opf.ts` — `findOpfSidecar`/`parseOpfMetadata`: detects a `<name>.opf` sidecar next to a `<name>.epub.txt` file and extracts Calibre's `<metadata>` block into the JSON shape `txtMetadata.content.metadata` stores. Parses with `@xmldom/xmldom`'s `DOMParser` (real, spec-following XML parsing — CDATA, comments, and attribute-quoting edge cases all just work, and malformed XML throws instead of silently mis-parsing) rather than a hand-rolled tag scanner; `onErrorStopParsing` (that package's own export) is passed as `onError` so a non-fatal `"error"`-level report throws too, not just a `"fatalError"` one.
- `txt/orphanSweep.ts` — `OrphanSweepTarget`: the shared shape (one row's own decrypted R2 prefix plus its known raw_keys) `bucket.ts`'s `resolveOwnedDocuments`/`resolveSharedDocuments` each build, one per owned document and one per share this admin created respectively, to compute `--clean-bucket`'s whole-account known-path set — a share's own R2 objects are swept via `sharedTxt.adminTxtKey`, never the recipient's `userTxtKey`.
- `txt/instantSignIn.ts` / `txt/firebaseAuth.ts` — Firebase password sign-in → InstantDB `auth.id` exchange (`signInToInstant`, for `--init-admin`).
- `txt/creds.ts` / `txt/initAdminCreds.ts` / `txt/scanCreds.ts` — creds.json loaders. `creds.ts` holds only the shared R2-config/field-validation helpers every other loader reuses; `InitAdminCreds` (initAdminCreds.ts) is the InstantDB-account shape (`--init-admin`) — also carries `slhdsa256fPrivKey`/`assetBaseUrl` through unvalidated, unused by `--init-admin`, purely so the same creds.json can double as `ui/`'s own build-creds.json (see README.md); `ScanCreds` (scanCreds.ts) is the smallest shape, just enough to enumerate every account via the Admin SDK and unwrap the admin's own key material, shared by `--clean-bucket`/`--update-db-catalog`/`--update-db-prefixHash`/`--ingest`.
- `leancrypto/` — vendored WASM leancrypto build, shared by `txt/` and `ui/` (`ui/src/data/leancrypto.ts` is the browser-side loader, mirroring `txt/crypto.ts`'s Node one). Not hand-authored here; treat as a build artifact (gitignored from prettier via `.prettierignore`, but tracked in git since there's no build step in this repo to regenerate it). Its `.d.ts` uses `export =` (CJS), not `export default` — this build is a genuine CommonJS module (`leancrypto/package.json`'s `"type": "commonjs"`), and `export default` there silently resolves to an uncallable type instead of a real error.
- `ui/src/data/session.ts` — the post-sign-in unwrap chain: queries `$users` (with its linked `keyStore`/`credStore`/`txtAccess`/`txtBookmarks`, client SDK, permission-rule-gated) and unwraps `user_root_key → umk → keyStore.privKey`/`credStore.content`/`txtAccess.content`/`txtBookmarks.content`. Also parses `credStore.content`'s own `r2_config` a second way (`r2Config.ts`'s `parseAdminR2WriteCreds`, alongside the ordinary `parseR2Config`), exposing the admin's real, static read-write R2 key pair as `Session.adminR2WriteCreds` when present (an admin's self row only) — the one static credential this app's browser code ever retains, used solely by `adminShares.ts`'s `grantShare`. `keyStorePrivKey` is currently unused (kept resolved against a future feature — sharing no longer Decapsulates anything). `txtAccess`/`txtBookmarks` may not exist yet (created lazily, on first write) — `resolveKeyedContent` mints a fresh key client-side in that case rather than failing. `reloadKeyedMaps` re-fetches just the latter two (cheaper than a full `resolveSession`) for `VaultContext.tsx`'s `refresh()`.
- `ui/src/data/library.ts` — `loadLibrary` resolves this account's whole library: every `txt` it owns plus every `sharedTxt` it owns (its own copy of something shared to it), each document's own root key (decrypt under `umk` either way — `txt.txtKey` or `sharedTxt.userTxtKey`, no Decapsulate involved anymore) and decrypted `txtMetadata.catalog`/`sharedTxtMetadata.catalog`. Full metadata content is fetched only by reader/edit flows. Returns `docKinds` (`"txt" | "sharedTxt"`) alongside `docKeys`, keyed the same way — a shared entry's own id is the `sharedTxt` row's id, never the source document's, since that's the row actually read from then on; `reader.ts`/`bookMetadata.ts`/`tempR2Creds.ts` all take this `kind` to know which table to query/authorize. Library queries use 1500-row pages, ordered by `seq`/`sharedTxt.shareKey` because an entity's built-in `id` cannot be used in an InstaQL `order` clause; other large admin/CLI scans use 1000-row pages.
- `ui/src/data/reader.ts` — `openDoc`/`partContent`: the read path once a document is open in the Reader — decrypts the row's own `prefix` and every part's own `txtPartKey` up front (one query), then decrypts one part's `path`/R2 object body on demand as the reader turns pages. `openDoc` takes a `kind` (`"txt" | "sharedTxt"`, from `library.ts`'s `docKinds`) and queries/decrypts against `txt`/`txtParts` or `sharedTxt`/`sharedTxtParts` accordingly — the decrypt chain itself is identical either way. Replaces the pre-port `owner.ts`/`parts.ts` (deleted).
- `ui/src/data/adminShares.ts` — `grantShare` implements the Sharing protocol (`docs/protocols.md`) entirely client-side: reads the source document's parts/metadata (skipping the AEAD layer's internal brotli step so already-compressed bytes need no recompression), recovers the recipient's `umk` (`adminUsers.ts`'s `getUserCreds`, then the ordinary `user_root_key -> umk` unwrap against the recipient's own `$users` row), mints a fresh root key/prefix/per-part key, wraps the root key both ways (`adminTxtKey` under the admin's own `umk`, `userTxtKey` under the recipient's), re-encrypts everything, uploads via `r2.ts`'s `buildAdminWriteClient`/`putObject` (the admin's real static credential, from `session.ts`'s `adminR2WriteCreds`), and commits one transact creating `sharedTxt`/`sharedTxtMetadata`/`sharedTxtParts`. Takes an optional `onProgress` callback (this codebase's usual convention — see `adminUsers.ts`'s `createUser`), wired into `BooksSection.tsx`'s Share panel. `revokeShare`/`listShares` operate on `sharedTxt` directly (a plain delete/paginated list) — no KEM, no `keyStore`, involved anywhere in this file.
- `ui/src/data/access.ts` / `bookmarks.ts` — pure read/modify/write functions over the one encrypted JSON blob each of `txtAccess`/`txtBookmarks` actually is (keyed by `txt_id`), enforcing the 10-entry/20-per-doc caps client-side. `state/VaultContext.tsx` is the only caller that ever re-encrypts and writes the result back.
- `ui/src/data/randomToken.ts` — browser port of `txt/randomToken.ts`'s `generateRandomToken`/`wrapToken`/`unwrapToken`, for `txt.prefix`/`txtParts.path`.
- `txt/instaqlPagination.ts` / `ui/src/data/instaqlPagination.ts` — generic, backend/shape-agnostic cursor-pagination loop (`collectAllPages`) for any query that could return thousands of rows for one account: the caller builds its own query for a given cursor and extracts `{rows, hasNextPage, endCursor}`, this just follows the cursor until exhausted. Not shared between the CLI and `ui/` (separate runtimes/tsconfigs, same as `base32.ts` already isn't) — two identical copies. `bucket.ts`'s (`resolveOwnedDocuments`/`resolveSharedDocuments`), `updateDbCatalog.ts`'s/`updateDbPrefixHash.ts`'s (`fetchTxtRows`), and `library.ts`'s (`loadOwnedDocs`/`loadSharedDocs`) own paged `txt`/`sharedTxt` queries are the current callers. `@instantdb/react`'s `queryOnce()` resolves `{data: {...}, pageInfo: {...}}` as _siblings_ (confirmed against `@instantdb/core`'s own type declarations) — `pageInfo` is never nested inside `data`, easy to get wrong by assumption.
- `ui/src/data/tempR2Creds.ts` — the only place this app builds an `AwsClient` from a _Worker-minted_ credential: POSTs `{instantToken, kind, id, prefix}` to `worker/r2Creds.ts`'s `/api/r2-creds` (`kind`: `"txt"` or `"sharedTxt"`, `id` that row's own id) and builds a client from the short-lived, read-only credential it returns, where `prefix` is that row's own already-decrypted `prefix` (a credential scopes to one document at a time, not a whole account). Bucket and endpoint are Worker configuration and are never request fields. `screens/Reader/useReaderBook.ts` mints (and reuses until near-expiry) one credential per opened document. `ui/src/data/r2.ts` also exports `buildAdminWriteClient`, the one place this app builds an `AwsClient` from a _static_ credential instead (`session.ts`'s `adminR2WriteCreds`) — used only by `adminShares.ts`'s `grantShare`, alongside that file's own `putObject`.
- `ui/src/state/VaultContext.tsx` — top-level unlock/session state, entirely on the main thread (no Worker/VFS to open). `unlock(file)` reads a creds.json-shaped file upload, signs into Firebase, exchanges for an InstantDB session (`session.ts`), and loads the whole library (`library.ts`) before marking the vault unlocked. `umk`/`keyStorePrivKey`/`credStoreKey`/`docKeys`/`txtAccess.key`/`txtBookmarks.key` are plain `Uint8Array`s with no wrapper/dispose mechanism — `lock()`, a failed `unlock()`, and `refresh()` (replacing a now-stale `docKeys`/`txtAccess`/`txtBookmarks`) all call `zeroBytes` (`crypto/bytes.ts`) on the ones being dropped before letting go of the reference, rather than relying on GC alone. This is best-effort only: it can't reach a copy held elsewhere (there shouldn't be one) and says nothing about the WASM crypto layer's own already-freed-unzeroed scratch buffers (`leancrypto.ts`).
- `ui/scripts/build-integrity.mjs` — runs after `vite build`: adds SRI to `dist/index.html`'s entry tags, writes `dist/manifest.json`/`.sig` (SLH-DSA-signed) and the real `dist/_headers` (CSP — the one Cloudflare actually serves, narrower than `index.html`'s own `<meta>` CSP), and bundles `creds/local_index.html` (a self-contained pre-verification page, never uploaded to the CDN).
- `worker/index.ts` — this deployment's only Worker script: dispatches `POST /api/r2-creds` itself, falls through to `env.ASSETS.fetch()` (the `dist/` static build) for everything else. Deployed as a real Worker-with-static-assets resource, not classic Cloudflare Pages Functions.
- `worker/r2Creds.ts` — authorizes via InstantDB itself, not a Firebase JWT: re-queries the caller's requested row (`kind`: `"txt"` or `"sharedTxt"`, `id` that row's own id) through InstantDB's Admin HTTP API with `As-Token: <the caller's own InstantDB session token>` and no admin credential, so that entity's ordinary `view` permission rule (`isAdmin || isOwner`, identical for both) decides access — an absent or permission-filtered row is indistinguishable, both just fail the check. Only once that query's returned `prefixHash` matches a hash the Worker computes itself over the request's own supplied `prefix` does it mint a temporary, always-read-only R2 credential for that prefix via R2's local JWT-signing scheme (HS256, no outbound Cloudflare API call) — this endpoint never mints a write-capable credential for anyone, admin included; `--ingest` writes with the admin's own real, static credential directly from the CLI, and sharing's own write step (`docs/protocols.md`'s Sharing protocol) now does the same from the admin's _browser_ session instead — see `docs/r2_credentials.md`'s design note on that deliberate exception.
- `wrangler.jsonc` — Worker config (`main`: `worker/index.ts`, `assets.directory`: `./dist`). Its own `"name"` is an unused placeholder; the real deploy target always comes from `scripts/deploy.sh`'s required `WORKER_NAME` env var, never this file.

## Non-obvious constraints (confirmed empirically — don't re-derive, don't assume otherwise)

- **InstaQL always returns a linked sub-entity as an array**, regardless of that link's own declared cardinality (`has: "one"` included). `$users.keyStore[0].id`, not `$users.keyStore.id` (`ui/src/data/session.ts`'s `firstLinked` guards every linked row for exactly this reason) — treating it as a plain object produces silently `undefined` fields rather than an error, which can propagate a long way before surfacing. See the `instantdb-instaql-array-links` memory.
- **An entity's own built-in `id` cannot be used in an InstaQL `order` clause** — confirmed against a real InstantDB app: `order: { id: "asc" }` fails with "The `txt.id` attribute is not indexed... not typed. Only indexed and typed attributes can be used to order by." Only real, declared attributes (`.indexed()`, or `.unique().indexed()`) are sortable this way. `bucket.ts`'s `resolveOwnedDocuments`, `updateDbCatalog.ts`'s/`updateDbPrefixHash.ts`'s `fetchTxtRows`, and `ui/src/data/library.ts`'s `loadOwnedDocs` all paginate `txt` by `seq` instead for exactly this reason (a plaintext, admin-assigned incrementing integer `--ingest` sets on every document it creates); `bucket.ts`'s `resolveSharedDocuments` and `library.ts`'s `loadSharedDocs` paginate `sharedTxt` by its own `shareKey` instead, since a share has no such ordinal.
- **`@instantdb/core`'s `Reactor` is browser-only** — its constructor checks `typeof window !== 'undefined' || typeof chrome !== 'undefined'` and silently skips storage/state setup (`this.kv`, etc.) when neither is true, later crashing deep inside `signInWithIdToken()` ("Cannot read properties of undefined (reading 'updateInPlace')") the first time anything touches that skipped state. `instantSignIn.ts` calls InstantDB's `POST /runtime/oauth/id_token` endpoint directly instead of using the SDK, for exactly this reason — don't use `@instantdb/core` in the CLI; use `@instantdb/admin` (Node-safe and permission-bypassing) or plain `fetch` for auth. The Cloudflare credential Worker does not use InstantDB at all.
- **Node's TypeScript strip-only mode doesn't support constructor parameter properties** (`constructor(private x: T)`) — a real syntax transform is needed, not just type erasure. Declare fields and assign in the constructor body instead.
- **R2 round-trips are batched**, not serial or fully unbounded: `ingest.ts`'s own part uploads prepare everything up front (pure, no I/O) then issue round-trips `R2_BATCH_CONCURRENCY` (constants.ts) at a time via `Promise.all`.
- **This project's live Cloudflare resource is the newer unified "Workers with static assets" product, not classic Cloudflare Pages** — confirmed via its own dashboard error ("Variables cannot be added to a Worker that only has static assets") when no real Worker script was attached yet. This means `worker/`'s deploy shape is a single Worker entry script (`main` in `wrangler.jsonc`, dispatching routes itself and falling through to `env.ASSETS.fetch()`), not a Pages Functions `functions/` directory — don't reach for that convention here.
- **R2's Temporary Credentials "local signing" derivation** (`worker/r2Creds.ts`, no outbound call to Cloudflare's API) — the runnable reference is [developers.cloudflare.com/r2/examples/authenticate-r2-temp-credentials](https://developers.cloudflare.com/r2/examples/authenticate-r2-temp-credentials/); the prose-only `.../api/s3/temporary-credentials/` page is incomplete/misleading on its own (confirmed the hard way: an earlier implementation built from that page alone used the wrong claim name, was missing required claims entirely, and used the wrong base64 variant — all three produced the exact same unhelpful `<Error><Code>InvalidArgument</Code><Message>X-Amz-Security-Token</Message></Error>` from R2, regardless of which one was still wrong). Use `jose`'s `SignJWT` with claims `{bucket, scope, paths: {prefixPaths}}` (the field is `scope`, not `permission` — `permission` is the separate Temporary Credentials _API_'s own parameter name) plus registered claims `sub` (R2 account ID), `iss` (parent access key ID — this, not the request's own `accessKeyId`, is what R2 uses to look up which parent secret to re-verify the signature against), `aud` (the R2 endpoint's host), `iat`/`exp` via `setIssuedAt()`/`setExpirationTime()` (there is no `ttlSeconds` claim), signed HS256 with the parent secret access key. Then: `accessKeyId` = the parent access key ID reused as-is, `secretAccessKey` = the SHA-256 hex digest of the full signed JWT string, `sessionToken` = plain `base64("jwt/" + <signed JWT>)` (not base64url, despite that being a reasonable-looking guess).

## Verification

**`txt/` (the CLI)** has a real `vitest` suite under `tests/` (`npm run test`, or `npm run typecheck` for types only) alongside the same real-building-blocks philosophy `ui/`'s suite (below) uses: pure functions (`textproc.ts`, `opf.ts`) are tested directly against real input, and anything touching InstantDB/R2 mocks `@instantdb/admin`'s `init`/`tx`/`id` and `txt/r2.ts`'s `R2Client` (`tests/updateDbPrefixHash.test.ts`, `tests/ingest.test.ts`) — `ingest.test.ts` additionally uses identity crypto mocks (`blobEncrypt`/`blobDecrypt` as no-ops) since that suite is about `ingest.ts`'s own orchestration, not re-verifying the real AEAD. Beyond that committed suite, ad hoc verification against fuller fakes (a minimal hand-rolled HTTP mock S3 server, a stateful in-memory fake InstantDB admin object, `global.fetch` monkey-patched to redirect Firebase/InstantDB sign-in to a local mock) still lives outside the repo as one-off scripts (session scratchpad, not committed) — write new ones the same way for anything the committed suite doesn't already cover.

**`ui/`** has a real vitest suite (`npm run ui:test`) following the same real-building-blocks philosophy: a real `leancrypto` WASM module (`data/leancrypto.ts`, same build the CLI uses) for genuine AEAD/HKDF round-trips in tests, a fake `aws4fetch` client for R2 reads and writes (`reader.test.ts`, `r2.test.ts`), `adminShares.test.ts`'s identity-crypto mocking (`../crypto/blob`'s `encrypt`/`decrypt` as no-ops, the same convention `adminUsers.test.ts` already established for admin-side operations) plus a fake in-memory R2 object store for `grantShare`'s own re-encrypt-and-upload flow, and a stateful fake InstantDB client (`queryOnce`/`transact`) reducing the real `@instantdb/react` tx builder's `{__etype, __ops}` shape where a real query/write needs faking — same pattern as the CLI's own admin-SDK fakes, just for the client SDK. `npm run ui:typecheck` (`tsc -b`) and `npm run ui:build` (a real `vite build` + `build-integrity.mjs`, verified end to end against a throwaway `build-creds.json`) are both clean.

**`worker/`** has a real vitest suite (`npm run worker:test`, covering `worker/r2Creds.ts`'s `handleR2Creds` against a stubbed `fetch` for both `kind: "txt"` and `kind: "sharedTxt"`) plus `npm run worker:typecheck`; a real `wrangler dev` run (hitting `/api/r2-creds` with curl, checking the static-asset fallthrough) is what verification against the real Workers runtime itself has meant.

`npm run format` / `npm run format:check` (prettier, repo-wide) exist; run format after any edit.

Some things can't be mocked at the HTTP-protocol level without real credentials and need a real run against live infra, with any errors diagnosed from the actual stack trace: the real `@instantdb/admin`/`@instantdb/react` `init()` → live query/transact/storage calls, and `worker/r2Creds.ts`'s actual Firebase JWKS verification + R2 credential mint (a bogus/malformed token is easy to test locally; a real, valid one needs a real Firebase project).

## Commit conventions

Detailed commit messages (imperative subject, bullet-point body explaining what and why), **no AI/Claude attribution ever** (no `🤖 Generated with Claude Code`, no `Co-Authored-By: Claude`), always push after committing. A `/commit` skill (`.claude/commands/commit.md`) automates this.

## Secrets

`.gitignore` blocks all `*.json` except a short explicit allowlist (`package.json`, `package-lock.json`, `tsconfig.json`, `ui/tsconfig*.json`, `ui/src/**/*.json`) — this project repeatedly generates local creds-shaped JSON files with real secrets (Firebase passwords, InstantDB admin tokens, R2 keys, `ui/build-creds.json`'s own SLH-DSA private key). Never commit a JSON file containing real credentials; double-check contents before `git add` on anything JSON-shaped. `wrangler.jsonc` is a `.jsonc` file (unaffected by that `*.json` rule either way) and carries no secrets itself — `worker/r2Creds.ts`'s two real secrets are Cloudflare dashboard Secrets, never written to any file in this repo.
