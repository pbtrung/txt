# Protocols

The operational read/write/share/cleanup flows against the entities in [data_model.md](data_model.md), using the key hierarchy in [key_hierarchy.md](key_hierarchy.md). See [r2_credentials.md](r2_credentials.md) for how the R2 access these flows depend on is actually brokered.

## Ingest / write path

There is no MVCC/version CAS: a `txtParts` row is written exactly once and never revised in place, so there's no concurrent-writer conflict to resolve on write.

`txt.ts --ingest` (admin only -- a `user`-typed account has no ingest path of its own) is this flow, one source `.txt` file at a time:

1. Clean and split the source text into ordered parts (`txt/textproc.ts`'s `preprocessText`/`splitParts`, target size per `constants.PART_TARGET`). Generate this document's `txtKey`, its `prefix = crockford_base32_lowercase(32 random bytes)`, and `prefixHash = Base64(SHA-256(UTF-8(prefix)))` -- the key and prefix are generated once per document, while the hash is their deterministic Worker-verification commitment. For each part, also generate a fresh `txtPartKey` (128 random bytes).
2. For each part: brotli-compress the cleaned text, encrypt it under that part's own `txtPartKey` (`crypto.md`'s Encrypt), and `PUT` the resulting ciphertext to R2 at `"${prefix}/${raw_key}"` for a freshly generated `raw_key = crockford_base32_lowercase(32 random bytes)`, using the admin's own real, static read-write R2 credential (from the admin's own self `credStore` row) — never a Worker-minted temporary one, since `worker/r2Creds.ts` only ever mints authorized read-only credentials (see [r2_credentials.md](r2_credentials.md)). All of a file's parts are uploaded before anything below is written.
3. Encrypt `raw_key` alone under that same `txtPartKey` and base64-encode the result — this becomes the new `txtParts` row's `path` value.
4. Only once every part from step 2 has uploaded successfully: one `db.transact([...])` creates the `txt` row (`prefix` from step 1 wrapped under `txtKey`, plaintext `prefixHash` from step 1, and `seq` -- the next integer after this admin's current highest, per `data_model.md`'s `txt` entity), its `txtMetadata` row, and every new `txtParts` row, all together. The metadata row stores both `content` — the original filename plus any Calibre `.opf` sidecar fields (`txt/opf.ts`, for a `.epub.txt` file) — and `catalog` — the lightweight `{name, title, authors, subjects, publishers}` projection used by library loading; both are wrapped directly under `txtKey`. Each `txtParts` row carries `partKey` (from `data_model.md`'s composite-uniqueness table), `txtPartKey` from step 1 wrapped under `txtKey`, and `path` from step 3, linked to `txt`.

**The one failure mode:** step 2 (the R2 `PUT`s) and step 4 (the InstantDB `transact`) are two separate operations. A crash between them — or a transact that fails outright after every part uploaded — leaves real R2 objects with no `txtParts` row pointing at them. `--ingest` does not attempt to clean these up itself: the orphan sweep below (`txt.ts --clean-bucket`) does. This is also why `--ingest`'s resumability is by filename, not by partially-committed state: a file that fails midway is retried from scratch on the next run, since nothing about it was ever recorded in InstantDB to resume from.

## Library/catalog load path

Library loading should query the readable documents — owned `txt` rows plus this account's own `sharedTxt` rows — with only the key material needed to unwrap each row's own root key and its metadata row's `catalog`. It should not fetch or decrypt full `txtMetadata.content`/`sharedTxtMetadata.content` for the book list. Both queries resolve the same way: decrypt the row's own root key directly under `owner`'s `umk` (`txt.txtKey`, or `sharedTxt.userTxtKey` for a share — no different mechanically, just a different field on a different table), then decrypt `catalog` under that key (`txtMetadata.catalog`, or `sharedTxtMetadata.catalog`) and render the list from that projection.

Use 1500 rows per InstantDB page for the owned/shared library queries. Other large admin and CLI scans use 1000 rows per page. These are throughput settings, not schema invariants.

## Read path

Query `txtParts` for `txt = target, partNum = N` (or a range) — the result already includes `txtPartKey` and `path`. Decrypt the target `txt` row's `prefix` directly under `txtKey`, decrypt this part's `txtPartKey` under that same `txtKey`, then decrypt `path` under that `txtPartKey` to recover `raw_key`. Before the direct R2 read, request a prefix-scoped credential from the Worker with `{instantToken, txtId, prefix}`; the Worker re-evaluates the caller's current `txt.view` permission and checks the supplied prefix against `txt.prefixHash`. Reassemble `raw_path = "${prefix}/${raw_key}"`, `GET` that object directly from R2 with the returned credential, then decrypt the object body under the same `txtPartKey` and brotli-decompress. The credential is reused for other parts of that document until near expiry; object bodies do not transit the Worker. Reading a shared document runs this exact sequence against `sharedTxt`/`sharedTxtParts` instead of `txt`/`txtParts` (and sends `sharedTxtId` in place of `txtId`) — the recipient owns that row outright, so there is no separate branch for "reading a share" versus "reading an owned document," only a different table.

The reader screen fetches full `txtMetadata.content` only when it needs the complete metadata record, not as part of the initial library list. Metadata editing follows the same rule: fetch and decrypt `content`, apply the edit, recompute `catalog` from the edited content, then update both `txtMetadata.content` and `txtMetadata.catalog` together in one transaction.

## Sharing protocol

**Not yet implemented** — `sharedTxt`/`sharedTxtParts` don't exist in `instant.schema.ts` yet; today's code shares by KEM-rewrapping the source document's own `txtKey` via a `txtShares` row (`ui/src/data/adminShares.ts`), granting the recipient direct read access to the admin's own `txt`/`txtParts`/`txtMetadata` rows. Everything below is the design to build against instead. Only the admin ever creates a share (`fromUser` is always the admin's own `$users` row):

1. Admin reads the source document in full — the same steps as the [Read path](#read-path) above: decrypt `txtKey` under its own `umk`, then every `txtParts` row's `txtPartKey`/`path`, `GET` and decrypt every object body, brotli-decompress. This yields the plaintext of every part.
2. Admin recovers the recipient's own `umk`: fetches its own admin-owned recovery `credStore` row for that recipient (`owner == admin`, `forUser == recipient`), decrypts that row's `content` (under its `credStoreKey`, wrapped under the admin's own `umk`) to read the recipient's `user_root_key`, then uses it to decrypt the recipient's `$users.umk` field directly — the same `user_root_key -> umk` unwrap [key_hierarchy.md](key_hierarchy.md) defines, just performed by the admin instead of the recipient's own client.
3. Admin generates this share's own fresh root key (128 random bytes, independent of the source document's `txtKey`), `prefix`/`prefixHash`, and (per part) a fresh `txtPartKey`.
4. Admin wraps that fresh root key two independent, purely symmetric ways — no KEM, no `keyStore`, involved: directly under its own `umk` (`sharedTxt.adminTxtKey`, exactly like `txt.txtKey` under its owner's `umk`), and directly under the recipient's own `umk` recovered in step 2 (`sharedTxt.userTxtKey`, the identical bytes, wrapped the same way).
5. For each part: brotli-compress the plaintext from step 1, encrypt it under that part's fresh `txtPartKey` (from step 3), and `PUT` it to R2 at `"${prefix}/${raw_key}"` for a freshly generated `raw_key`, using the admin's own real read-write R2 credential — the same upload mechanics as `--ingest`. All parts upload before anything is written to InstantDB. Also re-encrypt the source document's `txtMetadata.content`/`catalog` under the new root key to become this share's own `sharedTxtMetadata.content`/`catalog`.
6. Only once every part from step 5 has uploaded: one `db.transact([...])` creates the `sharedTxt` row (`txt` link to the source document, `owner` = recipient, `fromUser` = admin, `adminTxtKey`/`userTxtKey` from step 4, `prefix`/`prefixHash` from step 3, synthetic `shareKey`), the `sharedTxtMetadata` row (`sharedTxt` link, `owner` = recipient, `content`/`catalog` from step 5), and every `sharedTxtParts` row (`sharedTxt` link, `owner` = recipient, `partNum`, `txtPartKey` from step 3 wrapped under the new root key, `path` from step 5's `raw_key` wrapped under that part's own `txtPartKey`, synthetic `partKey`), all together.

This mirrors `--ingest`'s own upload-before-transact ordering and failure mode exactly (step 5's uploads and step 6's transact are separate operations; a crash between them leaves orphaned R2 objects for `--clean-bucket` to sweep, never a partially-recorded `sharedTxt`).

The recipient's read path for a shared document is then structurally identical to the owner's own read path above, against `sharedTxt`/`sharedTxtMetadata`/`sharedTxtParts` instead of `txt`/`txtMetadata`/`txtParts`: decrypt `userTxtKey` directly under their own `umk` — no different from unwrapping their own owned `txt.txtKey` — then everything below it unwraps exactly like an owned document. A recipient never reads the source `txt`/`txtParts`/`txtMetadata` rows at all — access to `sharedTxt`/`sharedTxtMetadata`/`sharedTxtParts` is a plain, single-hop `isOwner` check, the same shape as every other owner-gated entity in this design, not a two-hop grant onto someone else's rows.

## Revoking a share

**Not yet implemented**, same caveat as Sharing protocol above — describes the design to build against, not `ui/src/data/adminShares.ts`'s current `revokeShare`.

Revoking a share is a single step: delete the recipient's `sharedTxt` row (a plain `db.transact` from the admin's own browser session — no R2 access needed). InstantDB's cascade delete (`onDelete: "cascade"` on the `sharedTxt` link) removes every `sharedTxtMetadata`/`sharedTxtParts` row for it in the same operation. InstantDB stops returning the share to that recipient immediately, and the credential Worker refuses the next issuance/renewal because its user-scoped query for that `sharedTxt` id now returns no row.

This is already the complete revocation, with no second, best-effort content-rotation tier needed — a real design difference from a scheme where every recipient reads the same underlying document, not just a smaller version of the same idea. Because each recipient's `sharedTxt` copy has its own independent root key, `prefix`, and R2 objects — never shared with the source document or with any other recipient's own share of it — deleting this one row removes the _only_ record of where this recipient's content lives and the _only_ key that unwraps it (both wraps of it, `adminTxtKey` and `userTxtKey` alike). There is nothing left over for the revoked recipient's cached key or a still-live temporary R2 credential to open once cutover to nothing happens: the objects are still physically present in R2 until cleanup (below) gets to them, but nothing in InstantDB can ever again produce the prefix or per-part keys needed to address or decrypt them, for this recipient or anyone else. Revoking a second, third, or Nth recipient of the same document needs no special handling either, precisely because each recipient's revoke only ever touches that one recipient's own `sharedTxt` row — there is no shared state between concurrent revokes to coordinate.

A credential minted before the delete remains usable until its own short expiry (the same residual window [r2_credentials.md](r2_credentials.md) describes for any revocation), and none of this can erase plaintext, keys, paths, or ciphertext the recipient already downloaded while authorized — the one limitation that is fundamental to any system that ever let them read the content, not something a rekey could ever close. `txtAccess`/`txtBookmarks` entries are never wrapped under a document's `txtKey` (they're wrapped under the reading account's own `txtAccessKey`/`txtBookmarkKey`, unaffected by the revoke either way), so any entry they hold for that `txt_id` simply becomes a reference to a share that account can no longer open through the service — nothing to scrub.

The now-unreferenced R2 objects under that recipient's own, now-deleted `prefix` are not deleted by this step. Deleting the row already achieves the meaningful security property; actually reclaiming the R2 space is an availability/cost concern the standing orphan sweep (`--clean-bucket`, [Deletion and R2 cleanup](#deletion-and-r2-cleanup) below) already handles the same way it handles any other orphan, with the same grace period — no separate cleanup phase, staging area, or "pending" key is needed, because there was never a second copy of this recipient's content to cut over from in the first place.

## Deletion and R2 cleanup

Only the admin ever writes to R2, but there is no single admin-wide prefix to sweep anymore — every document has its own `prefix`. Document/part deletion (below) still only ever needs one document's own prefix at a time. The orphan sweep below is different: it needs to know about every owned document at once, because the only way to also catch an object sitting under a prefix no live `txt` row references at all (not just a crash-orphaned object under a prefix that's still live) is to list the bucket's entire flat R2 namespace once and diff it against the union of every document's own known paths, rather than listing one prefix at a time.

1. **Document/part deletion.** Deleting a `txt` row must delete every R2 object its `txtParts` rows point at — but InstantDB's own cascade-delete (`onDelete: "cascade"` on the `txt` link) will remove those `txtParts` rows the moment the `txt` row itself is deleted, which would destroy the only record of which `raw_key`s need deleting. Order matters: first decrypt the document's own `prefix` directly under `txtKey`, then each `txtParts` row's own `txtPartKey` (under that same `txtKey`) and its `path` (under that row's `txtPartKey`) to recover every `raw_key`, delete those R2 objects, and only then delete the `txt` row (letting cascade clean up `txtParts`/`txtMetadata`/every `sharedTxt` row sharing it — and, one level further, each of those `sharedTxt` rows' own `sharedTxtMetadata`/`sharedTxtParts` — for free). A crash between the R2 deletes and the `txt` row delete leaves a real document with dangling, already-gone R2 objects — recoverable by re-running the same delete (idempotent: deleting an already-gone R2 object is a no-op). Deleting the source document this way orphans every share's own R2 objects exactly the same way [Revoking a share](#revoking-a-share) does — the orphan sweep below picks them up.
2. **Orphan sweep**, for the ingest path's one failure mode (above) and for anything else in the bucket InstantDB doesn't currently account for: decrypt every admin-owned `txt` row's `prefix` and every one of its `txtParts` rows' own decrypted `raw_key` (each recovered via that row's own `txtPartKey`, unwrapped under `txtKey`), plus — since a share's content lives in R2 too, under its own independent prefix — every existing `sharedTxt` row's own `prefix` and each of its `sharedTxtParts` rows' own decrypted `raw_key` (unwrapped via that row's own `adminTxtKey`, never the recipient's `userTxtKey`; the admin needs no cooperation from any recipient to run this sweep). List the bucket's entire R2 namespace once, and delete whatever object key isn't in that known set — after a grace period long enough to outlast any in-flight ingest's or share's PUT-to-transact gap, since a part mid-upload looks identical to a stale one until its own transact commits. `txt.ts --clean-bucket` is this sweep, with a dry-run mode and confirmation prompt before deleting anything live.

There is no frontend R2-deletion path in the current design. A browser-side version would need a separate, explicit write-broker design for R2 deletion; it cannot reuse the authorized read-only temporary credentials from [r2_credentials.md](r2_credentials.md), and `ui/` must not use the admin's static `r2_config` directly.
