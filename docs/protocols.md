# Protocols

The operational read/write/share/garbage-collection flows against the entities in [data_model.md](data_model.md), using the key hierarchy in [key_hierarchy.md](key_hierarchy.md). See [r2_credentials.md](r2_credentials.md) for how the R2 access these flows depend on is actually brokered.

## Ingest / write path

There is no MVCC/version CAS: a `txtParts` row is written exactly once and never revised in place, so there's no concurrent-writer conflict to resolve on write.

1. (Admin only.) Clean and split the source text into ordered parts (target size per `constants.PART_TARGET`). For a brand-new document, generate its `txtKey`, its `prefix = crockford_base32_lowercase(32 random bytes)`, and `prefixHash = Base64(SHA-256(UTF-8(prefix)))` at this point too — the key and prefix are generated once per document, while the hash is their deterministic Worker-verification commitment. For each part, also generate a fresh `txtPartKey` (128 random bytes).
2. For each part: brotli-compress the cleaned text, encrypt it under that part's own `txtPartKey` (`crypto.md`'s Encrypt), and `PUT` the resulting ciphertext to R2 at `"${prefix}/${raw_key}"` for a freshly generated `raw_key = crockford_base32_lowercase(32 random bytes)`, using the admin's own real, static read-write R2 credential (from the admin's own self `credStore` row) — never a Worker-minted temporary one, since `worker/r2Creds.ts` only ever mints authorized read-only credentials (see [r2_credentials.md](r2_credentials.md)).
3. Encrypt `raw_key` alone under that same `txtPartKey` and base64-encode the result — this becomes the new `txtParts` row's `path` value.
4. `db.transact([...])`: for a brand-new document, create the `txt` row (`prefix` from step 1 wrapped under `txtKey`, plaintext `prefixHash` from step 1, and `sourceTxtId` too when this document came from `txt.ts --migrate`, per `data_model.md`'s `txt` entity) and its `txtMetadata` row in the same transaction. The metadata row stores both `content` — full name plus any OPF sidecar fields — and `catalog` — the lightweight `{name, title, authors, subjects, publishers}` projection used by library loading; both are wrapped directly under `txtKey`. Either way, create the new `txtParts` row (`partKey` from `data_model.md`'s composite-uniqueness table, `txtPartKey` from step 1 wrapped under `txtKey`, `path` from step 3, linked to `txt`).

**The one failure mode:** step 2 (the R2 `PUT`) and step 4 (the InstantDB `transact`) are two separate operations. A crash between them leaves a real R2 object with no `txtParts` row pointing at it. Garbage collection's orphan sweep (below) cleans this up.

## Library/catalog load path

Library loading should query the readable documents — owned `txt` rows plus incoming `txtShares` rows — with only the document key material needed to unwrap `txtKey` and `txtMetadata.catalog`. It should not fetch or decrypt full `txtMetadata.content` for the book list. After resolving each document's `txtKey` (owner decrypt under `umk`, share recipient Decapsulate via `txtShares`), decrypt `catalog` under that `txtKey` and render the list from that projection.

Use 1500 rows per InstantDB page for the owned/shared library queries. Other large admin and CLI scans use 1000 rows per page. These are throughput settings, not schema invariants.

## Read path

Query `txtParts` for `txt = target, partNum = N` (or a range) — the result already includes `txtPartKey` and `path`. Decrypt the target `txt` row's `prefix` directly under `txtKey`, decrypt this part's `txtPartKey` under that same `txtKey`, then decrypt `path` under that `txtPartKey` to recover `raw_key`. Before the direct R2 read, request a prefix-scoped credential from the Worker with `{instantToken, txtId, prefix}`; the Worker re-evaluates the caller's current `txt.view` permission and checks the supplied prefix against `txt.prefixHash`. Reassemble `raw_path = "${prefix}/${raw_key}"`, `GET` that object directly from R2 with the returned credential, then decrypt the object body under the same `txtPartKey` and brotli-decompress. The credential is reused for other parts of that document until near expiry; object bodies do not transit the Worker. The flow is otherwise identical whether the reader owns the document or is reading it via a `txtShares` grant; only how they obtained `txtKey` differs (own `umk` vs. Decapsulate).

The reader screen fetches full `txtMetadata.content` only when it needs the complete metadata record, not as part of the initial library list. Metadata editing follows the same rule: fetch and decrypt `content`, apply the edit, recompute `catalog` from the edited content, then update both `txtMetadata.content` and `txtMetadata.catalog` together in one transaction.

## Sharing protocol

Only the admin ever grants a share (`fromUser` is always the admin's own `$users` row):

1. Admin looks up the recipient's `keyStore.pubKey` (raw, not sensitive).
2. Admin Encapsulates against that `pubKey` (`crypto.md`'s Encapsulate) — this yields a KEM ciphertext `ct` and a shared secret `ss`, then wraps the document's already-unwrapped `txtKey` with the standard Encrypt procedure using `ss` as IKM. Encrypt generates and embeds its own random 64-byte `salt` in the resulting blob and derives the wrapping key via `HKDF-SHA3-512(IKM=ss, salt)`.
3. Admin writes the new `txtShares` row: `shareKey`, `txt` (link), `fromUser` = admin, `toUser` = recipient, `kemCt = ct`, `txtKey` = the blob from step 2. The blob already contains the salt needed to unwrap `txtKey`, so `kemCt` stores only the 1624-byte KEM ciphertext.
4. The recipient's own read path (above) tries their own-owned `txt` lookup first and falls back to Decapsulating a `txtShares` row scoped by `toUser.id == auth.id` when the document isn't their own — same pattern as the admin's own lookup, scoped by `owner.id` instead.

## Revoking a share

Revocation has two tiers: an immediate, always-effective authorization cutoff, and a slower, best-effort content rotation that closes what the first tier structurally cannot.

**Tier 1 — authorization revocation (immediate, unconditional).** A straight delete of the `txtShares` row (`ui/src/data/adminShares.ts`'s `revokeShare`, a plain `db.transact` from the admin's own browser session — no R2 access needed, so this tier never has to wait on the CLI). InstantDB stops returning the document to that recipient immediately, and the credential Worker refuses the next issuance/renewal because its user-scoped `txtId` query returns no row. Nothing else changes: the document's `txtKey`, `prefix`, and every part's ciphertext are untouched, so a credential minted before the delete remains usable until its own short expiry, and nothing about this tier can erase plaintext, keys, paths, or ciphertext the recipient already saved while authorized. `txtAccess`/`txtBookmarks` entries are never wrapped under `txtKey` (they're wrapped under the reading account's own `txtAccessKey`/`txtBookmarkKey`, unaffected by the revoke either way), so any entry they hold for that `txt_id` simply becomes a reference to a document that account can no longer open through the service — nothing to scrub, in either tier.

**Tier 2 — content rotation, best-effort (`node txt.ts --revoke-share <txtId> --to <email> --creds <creds.json>`).** Tier 1 alone leaves the actual bytes sitting at the document's current prefix completely unchanged, so anything the revoked recipient already holds that still points at them — a live temporary R2 credential, or (if it were somehow re-derived) the document's own `txtKey` — still opens real content. Because only the admin ever writes to R2 and `ui/` never holds a write-capable R2 credential (see [r2_credentials.md](r2_credentials.md)), closing that gap needs the CLI, as a deliberate follow-up action rather than something the browser revoke button can do by itself. `--revoke-share` rotates the whole document out from under every credential and key the revoked recipient might still have: a fresh `txtKey`, a fresh `prefix`/`prefixHash`, and a fresh `txtPartKey`/`path` (hence a brand-new R2 object) for every existing part, re-wrapped for every recipient who still holds a live `txtShares` row once cutover happens — the just-revoked recipient necessarily excluded, since their row is already gone — and only then deletes the old R2 objects.

It is "best-effort" in two specific senses, not a vague qualifier: it cannot retract content the recipient already downloaded while authorized (fundamental — see the limitations paragraph below), and it is allowed to fail, crash, or simply never be run without weakening tier 1's guarantee. Tier 1 already stands on its own the moment its own delete transact commits; `--revoke-share` can only make things stronger from there, never weaker, and every phase below is safe to interrupt and re-run from scratch.

Four phases, each resumable purely by re-inspecting the target `txt` row's and its `txtParts` rows' current state — no separate progress-tracking table, same philosophy as `--migrate`'s own resumability:

1. **Idempotent share delete.** Delete the `txtShares` row matching `{txt: txtId, toUser: <resolved from --to>}`, the same as tier 1 above. If no such row exists — the admin's UI already revoked it, or a previous, crashed `--revoke-share` run already got this far — that is treated as already-satisfied, not an error, and the command proceeds straight into staging. Either way, by the time any rekey work starts, the revoked recipient already has no path to a fresh credential; everything past this point is closing older, already-open windows, not opening new ones.

2. **Staging.** If `txt.pendingTxtKey` is unset, generate a fresh `txtKey`/`prefix`/`prefixHash` and, in one transact, write them as `pendingTxtKey`/`pendingPrefix`/`pendingPrefixHash` plus the document's _current_ `prefix` (decrypted under its current, still-live `txtKey`) as `staleR2Prefix` — all four wrapped as described in [data_model.md](data_model.md)/[key_hierarchy.md](key_hierarchy.md). If `pendingTxtKey` is already set (a resumed run, whether resumed because this same revoke crashed or because a second recipient was revoked while it was still in flight), reuse it and `pendingPrefix` as-is rather than minting new ones, which would orphan whatever the previous run already uploaded under the first `pendingPrefix`. Before doing any new work, sweep `pendingPrefix` the same way `orphanSweep.ts` sweeps a live prefix — diffed against every `txtParts` row that already has `pendingPath` set — to clean up any object a previous crash left behind between its own R2 `PUT` and the transact that would have recorded it (the same failure mode as the ingest path, [above](#ingest--write-path)). Then, for every `txtParts` row still missing `pendingPath`: decrypt its current `path`/`txtPartKey` under the document's _current, still-live_ `txtKey` (guaranteed untouched while any row remains unstaged — reveal, phase 3, never starts until every row is staged), `GET` and decrypt the object at the current prefix, re-encrypt it under a freshly generated `txtPartKey` (wrapped under `pendingTxtKey`), `PUT` it at `${pendingPrefix}/${new raw_key}`, and transact `pendingTxtPartKey`/`pendingPath` onto that row. Staging is fully non-disruptive: every live field (`txtKey`, `prefix`, every part's `txtPartKey`/`path`) is untouched throughout, so ordinary reads (owner or any current share recipient) keep working exactly as before for the whole phase, however long it takes — including reads by recipients who are not the one being revoked.

3. **Reveal.** Once every `txtParts` row has `pendingPath` set, cut the document over to the staged keys. Decrypt both the live `txtKey` and `pendingTxtKey` (both wrapped under `owner`'s `umk`, always independently recoverable) and compare their raw bytes: equal means a previous run already committed this step, so skip straight to the remaining chunk(s) below; not yet equal means this is the first (or only) reveal chunk, which additionally re-encrypts `txtMetadata.content`/`catalog` under `pendingTxtKey` and re-Encapsulates `pendingTxtKey` (`crypto.md`'s Encapsulate) against every `keyStore.pubKey` for every `txtShares` row still live on this `txt` at that moment (the just-revoked recipient's row, and any other already-revoked recipient's row, are simply absent from that set) — the `txt` row's own `txtKey`/`prefix`/`prefixHash` flip, the `txtMetadata` update, every rewrapped `txtShares` row, and the first `REVOKE_PARTS_PER_COMMIT`-sized batch of `txtParts` rows (flipped from their `pendingTxtPartKey`/`pendingPath` to live `txtPartKey`/`path`, with the `pending*` pair cleared) all commit together in one transact, exactly the way `--migrate`'s first per-document chunk bundles its own `txt`/`txtMetadata` rows with its first batch of parts. Every further chunk repeats only the plain per-`txtParts`-row flip, `REVOKE_PARTS_PER_COMMIT` rows at a time, until none remain with `pendingPath` set.

   **This is the one place this protocol cannot promise a fully atomic cutover for a document with more parts than one chunk holds**, an unavoidable consequence of the same "too many rows" per-transact ceiling `--migrate` already works around by chunking (`constants.MIGRATE_PARTS_PER_COMMIT`; a new `REVOKE_PARTS_PER_COMMIT` mirrors it here). Once the first chunk lands, the live `txtKey` is the new one, so any `txtParts` row not yet flipped in a later chunk is transiently unreadable — its `txtPartKey` is still wrapped under the _old_ `txtKey`, which is no longer live — until its own chunk commits. No data is destroyed or made unrecoverable by this: the old R2 objects for those rows are still sitting untouched at `staleR2Prefix` (phase 4 hasn't run yet), the new ciphertext for every row is already durably uploaded under `pendingPrefix` from staging, and re-running `--revoke-share` on this same `txtId` picks up exactly where a crash left off, using the still-set `pending*` fields as the source of truth for what's left — no re-encryption is needed on resume, only committing the remaining flips. For a document whose part count fits in one chunk, there is no such window at all — the whole cutover is one transact.

4. **Cleanup.** Once a fresh scan finds zero `txtParts` rows with `pendingPath` set, clear `txt.pendingTxtKey`/`pendingPrefix`/`pendingPrefixHash` in one transact — deliberately leaving `staleR2Prefix` set, since it is the only remaining record of which prefix's objects are now safe to delete. Before deleting anything, run one more safety check beyond the pendingPath scan above: list the new (now-live) `prefix` in R2 and confirm the object count matches this document's own `txtParts` row count. A mismatch means something upstream (a `PUT` that silently failed but was recorded as if it succeeded, external interference with the bucket) is inconsistent with what just got committed to InstantDB, and cleanup must stop and surface that instead of deleting a single old object — this check is cheap next to the delete it's gating, and it is the last backstop before doing something irreversible, satisfying this operation's top priority: never destroy the only remaining copy of a part's content on the strength of an assumption that turned out to be wrong.

   Cleanup then waits out a grace period — the same reasoning as the orphan sweep's own grace period below, long enough to outlast any read that was already in flight against the old prefix at the moment reveal committed — before listing and deleting every object under `staleR2Prefix` (unconditionally: nothing in InstantDB references that prefix anymore once the flip above committed). This delay exists for availability, not security: the security property tier 2 provides already took effect the instant `prefixHash` flipped in reveal, since the Worker (`r2_credentials.md`) refuses to mint any new credential scoped to the now-stale prefix from that point on — deleting the old objects sooner would not close the revoked recipient's access window any faster, it would only risk breaking a legitimate reader (the owner, or any recipient who wasn't revoked) who decrypted the old prefix and obtained a credential for it moments before cutover and is still mid-read. Only once the deletes finish without error does cleanup clear `staleR2Prefix` itself, in a final transact. A crash between deleting objects and clearing `staleR2Prefix` is safe to resume: a re-run sees `pendingTxtKey` already unset but `staleR2Prefix` still set, and knows the rekey itself is done and only cleanup remains, without starting a second, needless rekey.

Running `--collect-garbage` concurrently with an in-progress `--revoke-share` is safe: its per-document sweep only ever lists the target's _current, live_ `prefix`, never a `pendingPrefix` (not live yet) or an already-superseded `staleR2Prefix` (no longer referenced by that document's own `prefix` field, so outside what that sweep looks at either way) — the two operations simply never touch the same R2 namespace at the same time. Revoking a second recipient of the same document while a `--revoke-share` run is already mid-flight (or re-running it after a crash) needs no special handling either: phase 1's idempotent delete removes that second recipient's own `txtShares` row directly, and whichever rekey run is or becomes current simply re-reads the live `txtShares` set at its own reveal step, which by then already excludes every recipient revoked so far — one in-flight rekey run absorbs any number of revokes issued against the same document while it runs, rather than needing to be restarted per recipient.

**Limitations, stated plainly.** None of this retracts content the revoked recipient already downloaded while authorized — decrypted plaintext, an unwrapped `txtKey`, or raw R2 object bytes they saved locally are outside this design's reach the moment they leave the client, rekey or not; this is fundamental to any system that ever let them read the content, not a gap `--revoke-share` failed to close. Nor does it invalidate a still-live temporary R2 credential any faster than cleanup actually deletes the objects it's scoped to: `prefixHash` flips at reveal, so the Worker stops minting new credentials against the old prefix immediately, but a credential minted moments before reveal remains individually valid (per its own short TTL, [r2_credentials.md](r2_credentials.md)) until either it expires or its target objects are gone, whichever comes first — and cleanup deliberately waits out a grace period before deleting them, for the availability reason above. `--revoke-share` shrinks both windows relative to tier 1 alone — the "mint a fresh credential" window to effectively zero as of reveal, and the "an already-minted credential still works" window down to roughly the grace period plus the delete itself, instead of leaving the whole document indefinitely readable through the original prefix — but it does not, and structurally cannot, make either window provably zero. Running it is not optional busywork layered onto every revoke: it is what turns "this recipient can no longer get new access" into "this recipient's actual copy of the ciphertext is gone," for whichever revokes are sensitive enough to justify the operator cost.

## Garbage collection

Only the admin ever writes to R2, but there is no single admin-wide prefix to sweep anymore — every document has its own `prefix`, so both sweeps below iterate over every `txt` row (the admin can enumerate all of them; a `user` account never needs to run GC at all, since it never writes) rather than listing one shared namespace.

1. **Document/part deletion.** Deleting a `txt` row must delete every R2 object its `txtParts` rows point at — but InstantDB's own cascade-delete (`onDelete: "cascade"` on the `txt` link) will remove those `txtParts` rows the moment the `txt` row itself is deleted, which would destroy the only record of which `raw_key`s need deleting. Order matters: first decrypt the document's own `prefix` directly under `txtKey`, then each `txtParts` row's own `txtPartKey` (under that same `txtKey`) and its `path` (under that row's `txtPartKey`) to recover every `raw_key`, delete those R2 objects, and only then delete the `txt` row (letting cascade clean up `txtParts`/`txtMetadata`/`txtShares` for free). A crash between the R2 deletes and the `txt` row delete leaves a real document with dangling, already-gone R2 objects — recoverable by re-running the same delete (idempotent: deleting an already-gone R2 object is a no-op).
2. **Orphan sweep**, for the ingest path's one failure mode (above): for each `txt` row, decrypt its `prefix`, list every R2 object under that one prefix, diff against that document's own `txtParts` rows' decrypted `raw_key`s (each recovered via that row's own `txtPartKey`, unwrapped under `txtKey`), and delete whatever's left over after a grace period long enough to outlast any in-flight ingest's PUT-to-transact gap. Structurally the same shape as `txt.ts --clean-bucket`, just per-document instead of over one flat namespace.

`txt.ts --migrate` implements a version of sweep 2 scoped to its own target account, run at the start of every invocation (no grace period needed, since it's the same operator re-running the same command, not a background job racing an in-flight ingest): for each document already migrated, decrypt its `prefix`, list R2 objects under it, diff against that document's `txtParts` rows' decrypted `raw_key`s (via each row's own `txtPartKey`, as above), and delete leftovers from a previous crashed run. This is what makes `--migrate` resumable without duplicating documents: each migrated document's `txt` row carries the source snapshot's own `sourceTxtId` (`data_model.md`'s `txt` entity), so a re-run only needs to query the target for existing `sourceTxtId`s (and, for a document that already exists, a `COUNT` of its own `txtParts`) to know which source documents already made it across, and how far into a partially-committed one to resume from.

There is no frontend garbage collector in the current design. A browser-side version would need a separate, explicit write-broker design for R2 deletion; it cannot reuse the authorized read-only temporary credentials from [r2_credentials.md](r2_credentials.md), and `ui/` must not use the admin's static `r2_config` directly.
