# Auth

Every unlock requires a live Firebase sign-in (`getIdToken()` -> `db.auth.signInWithIdToken()`), since InstantDB resolves identity from the token's email claim at session-creation time, not from a long-lived static credential. The client retains the resulting InstantDB `user.refresh_token` in memory for the unlocked session: the same-origin credential Worker passes it to InstantDB as `As-Token` whenever it authorizes an R2 prefix, so the existing permission rules—not a duplicated Worker-side ownership/share predicate—decide whether the requested `txtId` is still readable. After sign-in, the client reads its own `$users.umk`, unwraps it under `user_root_key`, then reads its own `keyStore`/`credStore`/`txtAccess`/`txtBookmarks` rows (see [data_model.md](data_model.md)) as needed. For `credStore`, normal unlock uses the account's self row (`owner == forUser == auth.id`); admin-owned recovery rows for other users are queried by `forUser` only from Manage Users flows. Every role depends on the authorized temporary-credential intermediary (see [r2_credentials.md](r2_credentials.md)) for frontend R2 access — always read-only, and scoped to one currently readable document prefix.
