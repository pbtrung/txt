# Temporary, Prefix-Scoped R2 Credentials

How R2 access is brokered for the entities in [data_model.md](data_model.md), and how a new `user` account gets provisioned. See [protocols.md](protocols.md) for the ingest/read/share/GC flows this feeds into.

This endpoint is for the frontend (`ui/`) only, and it never mints a write-capable credential for anyone — the admin included. No account gets a static R2 access key in the browser: the admin's own `read_write_access_key_id`/`secret` is the only permanent R2 credential in this design, stored only in server/operator-controlled places (the Worker secret, local CLI credentials, and the admin's encrypted self `credStore` row), never in any client session. Every frontend read goes through a short-lived, prefix-scoped, **read-only** temporary credential instead — writing (ingest, see [protocols.md](protocols.md)) uses the admin's own real, static credential directly, never this Worker.

Every document's `raw_path` values live under its own `txt.prefix` — random, wrapped under that document's `txtKey`, and recoverable only by whoever can unwrap `txtKey` (the owner, or a share recipient via Decapsulate). This means a temporary credential can be scoped to exactly one document at a time, not to everything a given account can see: a `user` reading a shared document only ever needs (and only ever requests) a credential scoped to that one document's own `prefix`.

1. The client calls Firebase's `getIdToken()` and sends `{idToken, prefix}` to the Worker's `POST /api/r2-creds`, where `prefix` is a document's own decrypted `txt.prefix`. The R2 bucket and endpoint are Worker-side configuration (`R2_BUCKET`, `R2_ENDPOINT`), never client-supplied.
2. The Worker verifies the token itself — RS256 signature against Firebase's own public JWKS via `jose`, issuer/audience pinned to a Worker-configured Firebase project ID never accepted from the request itself.
3. **The Worker mints `scope: "object-read-only"` unconditionally** — for any verified identity (admin or `user`-role alike), on any requested `prefix`. It does not cross-check the requested `prefix` against InstantDB or against the token's own subject; the Worker intentionally never talks to InstantDB. The simple design treats possession of a decrypted `txt.prefix` as a bearer read capability for R2 ciphertext access. This is acceptable only because prefixes are random, stored encrypted under `txtKey`, and every object body remains encrypted under its part's own `txtPartKey`: a leaked or forged `prefix` can let any authenticated caller fetch encrypted objects under that prefix until the prefix is rotated, but it does not grant write access and does not by itself decrypt document text.
4. The Worker mints the temporary credential via R2's Temporary Credentials local-signing path (see the current `worker/r2Creds.ts` implementation notes for the exact JWT claim shapes) using that read-only `scope`, and returns `{accessKeyId, secretAccessKey, sessionToken, expiresAtMs}`.
5. The client re-requests a fresh temporary credential before `expiresAtMs`; no long-lived secret is ever cached client-side.

This is the one place this design needs a server component — every other unlock/read/write path is a direct client-to-InstantDB or client-to-R2 call (ingest included: the admin's own real credential, used directly by the CLI, not brokered through this Worker). The Worker only ever verifies identity and brokers scoped, time-limited, read-only credentials; it never sees page content or any account's `umk`/`txtKey`, and it never grants write access to anyone.

**`ui/` never holds a static R2 credential, admin session included.** Even though the admin's own real `r2_config` is technically recoverable client-side (decrypt `umk` -> the admin's own self `credStore` row, where `owner == forUser == admin`), `ui/` never builds an R2 client from it directly — every read, for every role, goes through this same temporary-credential broker. Garbage collection stays CLI/operator-side in the current design because deleting R2 objects requires read-write credentials, and this Worker deliberately only mints read-only temporary credentials.

## Provisioning a `user` account

Creating a `user` account is an admin-side action: the admin generates that user's `user_root_key` (delivered to them out-of-band via their own `creds.json`), generates their `umk` and wraps it under that `user_root_key`, generates their `keyStore` keypair (`keyStoreKey` wrapped under their `umk`, `privKey` wrapped under `keyStoreKey`), and writes the user's own `credStore` row (`owner == forUser == user`, fresh `credStoreKey` wrapped under the user's `umk`). The admin also writes an admin-owned recovery row for that same user (`owner == admin`, `forUser == user`, a different fresh `credStoreKey` wrapped under the admin's `umk`) whose plaintext `content` is the admin-only backup/edit credential bundle: Firebase app/client/email/password/API key and `user_root_key`. The recovery row does not duplicate `display_name` or `user_auth_id`: identity comes from the plaintext `forUser` link, and the canonical display name is stored only in the user's own self `credStore.content`. That `forUser` link is what lets Manage Users retrieve the target user's saved credentials for backup, recovery, or edit without scanning and decrypting every admin-owned credential row. There is no per-user database to initialize and no initial page upload — a fresh `user` account owns no documents at all until the admin shares one with them. From that point on, the user reads shared documents entirely through the temporary-credential flow above.

## Design notes

- **Two independent boundaries limit what a compromised or malicious `user` session can do, not just one.** `worker/r2Creds.ts` never mints write-capable credentials for anyone, so a share recipient can't overwrite or delete a document's parts no matter which `prefix` it names. Per-document R2 prefixes are the second, narrower boundary on top of that: even the _read_ access a temporary credential grants is scoped to one document's own `prefix`, never the admin's whole corpus.
