# Authorized, Prefix-Scoped R2 Credentials

How R2 access is brokered for the entities in [data_model.md](data_model.md), and how a new `user` account gets provisioned. See [protocols.md](protocols.md) for the ingest/read/share/GC flows this feeds into.

This endpoint is for the frontend (`ui/`) only, and it never mints a write-capable credential for anyone — the admin included. No frontend R2 client uses a static access key. Every frontend read uses a short-lived, prefix-scoped, **read-only** temporary credential authorized against the caller's current InstantDB permissions; writing (ingest, see [protocols.md](protocols.md)) uses the admin's own real, static credential directly, never this Worker.

Every document's `raw_path` values live under its own `txt.prefix` — random, wrapped under that document's `txtKey`, and recoverable only by whoever can unwrap `txtKey` (the owner, or a share recipient via Decapsulate). The same `txt` row also stores `prefixHash = Base64(SHA-256(UTF-8(prefix)))` in plaintext. This commitment does not reveal a 32-random-byte prefix, but lets the Worker bind a client-supplied decrypted prefix to the authorized `txtId`; checking `txtId` alone would let a caller pair one still-readable document ID with a cached prefix from a revoked document.

1. The client sends `{instantToken, txtId, prefix}` to the Worker's `POST /api/r2-creds`, where `instantToken` is the signed-in account's InstantDB refresh token and `prefix` is that document's decrypted `txt.prefix`. The R2 bucket and endpoint are Worker-side configuration (`R2_BUCKET`, `R2_ENDPOINT`), never client-supplied.
2. The Worker queries exactly that `txtId` through InstantDB's Admin HTTP API with `As-Token: instantToken` and no admin credential. InstantDB evaluates the normal `txt.view` permission rule, so the query returns the row only while the caller is its owner/admin or has a live `txtShares` grant.
3. The Worker computes `Base64(SHA-256(UTF-8(prefix)))` itself and compares it with the returned row's authoritative `prefixHash`. A missing row or mismatch returns the same `403` response. The client never supplies the trusted hash.
4. Only after both checks pass, the Worker locally signs an R2 temporary credential with `scope: "object-read-only"` and `paths.prefixPaths = ["${prefix}/"]`, returning `{accessKeyId, secretAccessKey, sessionToken, expiresAtMs}`.
5. The browser uses that credential to fetch document parts directly from R2. It re-requests a credential before `expiresAtMs`; each renewal repeats the InstantDB authorization and prefix-binding checks.

Deleting a `txtShares` row prevents the recipient from obtaining another credential for that document. A credential minted before deletion remains usable until its short expiry, and neither expiration nor revocation can erase plaintext, keys, paths, or ciphertext the recipient saved while authorized. This design provides bounded-latency revocation of future R2 access, not retraction of already disclosed content. `txt.ts --revoke-share` ([protocols.md](protocols.md)'s Revoking a share) tightens this further, best-effort: once its reveal phase flips the document's `prefixHash`, this check (step 3) starts refusing even a request that still supplies the revoked recipient's cached, previously-valid decrypted prefix — ahead of that prefix's own R2 objects actually being deleted, not only after. A credential minted for the old prefix in the moments before that flip still decrypts real objects until cleanup actually deletes them (deliberately delayed by a grace period; see protocols.md), so the two mechanisms close different windows: `prefixHash` closes the "mint a new credential" window immediately, cleanup's delete closes the "an already-minted credential still works" window some time later.

This is the one place this design needs a server component — every other unlock/read/write path is a direct client-to-InstantDB or client-to-R2 call (ingest included: the admin's own real credential, used directly by the CLI, not brokered through this Worker). The Worker authorizes and locally signs scoped, time-limited, read-only credentials; it never sees page content or any account's `umk`/`txtKey`/`txtPartKey`, and it never grants write access.

**`ui/` never retains or uses a static R2 credential as session state, admin session included.** The admin's self `credStore.content` combines connection fields and static keys in one encrypted JSON payload, so admin unlock transiently decrypts plaintext containing those keys before `parseR2Config` selects only `endpoint`/`region`/`bucket`. The access-key fields are discarded and are never used to build a frontend R2 client. This means a compromised admin browser runtime could still capture them during unlock; eliminating that exposure would require separating browser connection data from the operator credential payload. Every actual frontend R2 read, for every role, uses an authorized temporary credential. R2 object deletion stays CLI/operator-side because it requires read-write credentials, and this Worker deliberately only mints read-only temporary credentials.

## Provisioning a `user` account

Creating a `user` account is an admin-side action: the admin generates that user's `user_root_key` (delivered to them out-of-band via their own `creds.json`), generates their `umk` and wraps it under that `user_root_key`, generates their `keyStore` keypair (`keyStoreKey` wrapped under their `umk`, `privKey` wrapped under `keyStoreKey`), and writes the user's own `credStore` row (`owner == forUser == user`, fresh `credStoreKey` wrapped under the user's `umk`). The admin also writes an admin-owned recovery row for that same user (`owner == admin`, `forUser == user`, a different fresh `credStoreKey` wrapped under the admin's `umk`) whose plaintext `content` is the admin-only backup/edit credential bundle: Firebase app/client/email/password/API key and `user_root_key`. The recovery row does not duplicate `display_name` or `user_auth_id`: identity comes from the plaintext `forUser` link, and the canonical display name is stored only in the user's own self `credStore.content`. Manage Users does not decrypt that target-owned self row to recover `display_name`; admin list/edit screens use non-secret account identity such as `$users.email`. That `forUser` link is what lets Manage Users retrieve the target user's saved credentials for backup, recovery, or edit without scanning and decrypting every admin-owned credential row. There is no per-user database to initialize and no initial page upload — a fresh `user` account owns no documents at all until the admin shares one with them. From that point on, the user reads shared documents entirely through the temporary-credential flow above.

## Design notes

- **Three checks limit what a compromised or malicious `user` session can do.** InstantDB must still consider the requested `txtId` readable, its stored `prefixHash` must match the supplied prefix, and `worker/r2Creds.ts` only mints a read-only credential scoped to that one prefix. A share recipient therefore cannot use one valid share to authorize a different document's cached prefix, and cannot overwrite or delete objects through the frontend credential.
