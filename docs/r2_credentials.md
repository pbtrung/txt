# Authorized, Prefix-Scoped R2 Credentials

How R2 access is brokered for the entities in [data_model.md](data_model.md), and how a new `user` account gets provisioned. See [protocols.md](protocols.md) for the ingest/read/share/GC flows this feeds into.

This endpoint is for the frontend (`ui/`) only, and it never mints a write-capable credential for anyone — the admin included. No frontend R2 client uses a static access key. Every frontend read uses a short-lived, prefix-scoped, **read-only** temporary credential authorized against the caller's current InstantDB permissions; writing (ingest, see [protocols.md](protocols.md)) uses the admin's own real, static credential directly, never this Worker.

Every document's `raw_path` values live under its own `prefix` — random, wrapped under that row's own root key, and recoverable only by whoever can unwrap it (a `txt`'s owner; a `sharedTxt`'s owner, or the admin, via `adminTxtKey`/`userTxtKey` — see [data_model.md](data_model.md)). The same row also stores `prefixHash = Base64(SHA-256(UTF-8(prefix)))` in plaintext. This commitment does not reveal a 32-random-byte prefix, but lets the Worker bind a client-supplied decrypted prefix to the authorized row; checking the row's id alone would let a caller pair one still-readable id with a cached prefix from a revoked one.

1. The client sends `{instantToken, kind, id, prefix}` to the Worker's `POST /api/r2-creds`, where `instantToken` is the signed-in account's InstantDB refresh token, `kind` is `"txt"` or `"sharedTxt"` (which entity to query — reading an owned document versus reading a share are otherwise identical requests, just against different tables), `id` is that row's own id, and `prefix` is that row's decrypted `prefix`. The R2 bucket and endpoint are Worker-side configuration (`R2_BUCKET`, `R2_ENDPOINT`), never client-supplied.
2. The Worker queries exactly that row, from the table `kind` names, through InstantDB's Admin HTTP API with `As-Token: instantToken` and no admin credential. InstantDB evaluates that entity's normal `view` permission rule (`isAdmin || isOwner` for both `txt` and `sharedTxt`, [data_model.md](data_model.md)'s Permission rules), so the query returns the row only while the caller is its owner or the admin.
3. The Worker computes `Base64(SHA-256(UTF-8(prefix)))` itself and compares it with the returned row's authoritative `prefixHash`. A missing row or mismatch returns the same `403` response. The client never supplies the trusted hash.
4. Only after both checks pass, the Worker locally signs an R2 temporary credential with `scope: "object-read-only"` and `paths.prefixPaths = ["${prefix}/"]`, returning `{accessKeyId, secretAccessKey, sessionToken, expiresAtMs}`.
5. The browser uses that credential to fetch document or share parts directly from R2. It re-requests a credential before `expiresAtMs`; each renewal repeats the InstantDB authorization and prefix-binding checks.

Deleting a `sharedTxt` row prevents the recipient from obtaining another credential for that share, immediately and completely — not just a bounded-latency cutoff pending a later content rotation. A credential minted before deletion remains usable until its short expiry, and neither expiration nor deletion can erase plaintext, keys, paths, or ciphertext the recipient saved while authorized. What makes this already-complete, unlike revoking one recipient's access to a document every recipient reads the same copy of, is structural: a `sharedTxt` row is the _only_ record of where that recipient's copy of the content lives and the _only_ recoverable copy of the key that unwraps it (see [protocols.md](protocols.md)'s Revoking a share) — deleting it, rather than rotating anything, is already sufficient.

This is the one place this design needs a server component — every other unlock/read/write path is a direct client-to-InstantDB or client-to-R2 call (ingest included: the admin's own real credential, used directly by the CLI, not brokered through this Worker). The Worker authorizes and locally signs scoped, time-limited, read-only credentials; it never sees page content or any account's `umk`/`txtKey`/`txtPartKey`, and it never grants write access.

**`ui/` never retains or uses a static R2 credential as session state, admin session included.** The admin's self `credStore.content` combines connection fields and static keys in one encrypted JSON payload, so admin unlock transiently decrypts plaintext containing those keys before `parseR2Config` selects only `endpoint`/`region`/`bucket`. The access-key fields are discarded and are never used to build a frontend R2 client. This means a compromised admin browser runtime could still capture them during unlock; eliminating that exposure would require separating browser connection data from the operator credential payload. Every actual frontend R2 read, for every role, uses an authorized temporary credential. R2 object deletion stays CLI/operator-side because it requires read-write credentials, and this Worker deliberately only mints read-only temporary credentials.

## Provisioning a `user` account

Creating a `user` account is an admin-side action: the admin generates that user's `user_root_key` (delivered to them out-of-band via their own `creds.json`), generates their `umk` and wraps it under that `user_root_key`, generates their `keyStore` keypair (`keyStoreKey` wrapped under their `umk`, `privKey` wrapped under `keyStoreKey`), and writes the user's own `credStore` row (`owner == forUser == user`, fresh `credStoreKey` wrapped under the user's `umk`). The admin also writes an admin-owned recovery row for that same user (`owner == admin`, `forUser == user`, a different fresh `credStoreKey` wrapped under the admin's `umk`) whose plaintext `content` is the admin-only backup/edit credential bundle: Firebase app/client/email/password/API key, `display_name`, and `user_root_key`. `display_name` is written once at creation as a copy of the same value put in the user's own self row (below); Manage Users' list/edit screens read this copy — never the target-owned self row, which only that user's own `umk` can unwrap — and treat it as read-only after creation. The recovery row still does not duplicate `user_auth_id`: identity comes from the plaintext `forUser` link. That `forUser` link is what lets Manage Users retrieve the target user's saved credentials for backup, recovery, or edit without scanning and decrypting every admin-owned credential row. There is no per-user database to initialize and no initial page upload — a fresh `user` account owns no documents at all until the admin shares one with them. From that point on, the user reads shared documents entirely through the temporary-credential flow above.

## Design notes

- **Three checks limit what a compromised or malicious `user` session can do.** InstantDB must still consider the requested `id` (a `txt` or `sharedTxt` row) readable, its stored `prefixHash` must match the supplied prefix, and `worker/r2Creds.ts` only mints a read-only credential scoped to that one prefix. A share recipient therefore cannot use one valid share to authorize a different document's or share's cached prefix, and cannot overwrite or delete objects through the frontend credential.
